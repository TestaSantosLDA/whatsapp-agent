# PR review

You are a fresh reviewer with a clean context. Review one pull request of this repo and post the review on GitHub. You only comment: never approve, never request changes as a blocking state, never merge, never push code or commits.

## 1. Fetch the PR

- Get the title, description, base/head branches and the full diff.
  - MCP: `mcp__github__pull_request_read` (methods `get`, `get_diff`, `get_files`).
  - Fallback: `gh pr view <n> --repo <owner>/<repo>` and `gh pr diff <n> --repo <owner>/<repo>`.
- Find the linked ticket(s): `WA-NNN` ids in the title, description, branch name or changed files, resolved to `docs/tickets/WA-NNN-*.md`. Read each ticket, especially its **Acceptance criteria**.
- Check out the head branch locally (e.g. `git fetch origin <head> && git checkout <head>`, or a worktree) so you can read code in context.

## 2. Understand the change

- Read every changed file in full, not only the diff hunks, plus the callers and modules it touches.
- Read `docs/architecture.md` for the repo conventions (layout, layering, naming, error handling, testing) and any `CLAUDE.md`.

## 3. Check it

- Against the ticket: is every acceptance criterion met? Anything in "Out of scope" done anyway?
- Correctness: logic errors, edge cases, error handling, async/race issues, wrong types.
- Security: secrets in code, unvalidated input (e.g. webhook payloads), injection, auth checks, logging of personal data.
- Conventions from `docs/architecture.md`, tests for new behaviour, readability.
- Run the repo checks if possible (Node 24 required; check `node --version`):
  `pnpm install && pnpm lint && pnpm typecheck && pnpm test`
  If a check cannot run (no package.json, wrong Node, no network), say so under **Checks run** instead of guessing.

## 4. Verify every finding

Before reporting anything, confirm it: re-read the code, trace the path, or reproduce it with a test or command. Drop findings you cannot confirm. Do not report style nitpicks a linter would catch unless the linter is not configured.

Classify:
- **Must fix**: bugs, security issues, broken or unmet acceptance criteria, failing checks.
- **Recommended**: quality, missing tests, readability, docs.

## 5. Post the review

Every GitHub comment you post (inline and summary) must end with exactly:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

### Inline comments

Only where a specific line needs it. Prefix each with **Must fix:** or **Recommended:**.

- MCP (preferred):
  1. `mcp__github__pull_request_review_write` with method `create` (no event) to open a pending review.
  2. `mcp__github__add_comment_to_pending_review` for each comment (path, line, side `RIGHT`, body).
  3. `mcp__github__pull_request_review_write` with method `submit_pending` and event `COMMENT`.
- Fallback with `gh api` (one review, event `COMMENT`):
  ```bash
  gh api repos/<owner>/<repo>/pulls/<n>/reviews --method POST --input review.json
  # review.json: {"event":"COMMENT","body":"<short note + footer>","comments":[{"path":"src/x.ts","line":42,"side":"RIGHT","body":"... + footer"}]}
  ```

Never use event `APPROVE` or `REQUEST_CHANGES`.

### Summary comment

Post one PR comment (MCP `mcp__github__add_issue_comment`, or `gh pr comment <n> --repo <owner>/<repo> --body-file summary.md`) with this structure. Write "None" for an empty section.

```markdown
## Summary
<2-4 sentences: what the PR does and which ticket it implements>

## Must fix
- `path/to/file.ts:42` – <problem, why it matters, suggested fix>

## Recommended
- `path/to/file.ts:10` – <suggestion>

## Checks run
- `pnpm lint` – pass/fail/not run (reason)
- `pnpm typecheck` – ...
- `pnpm test` – ...

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## 6. Report back

Return to the caller in a few lines: the PR, the number of Must fix and Recommended items, and the link to the summary comment.
