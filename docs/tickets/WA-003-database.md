# WA-003: Database schema and migrations

| Status    | Milestone | Depends on | PR  |
| --------- | --------- | ---------- | --- |
| in review | M1        | WA-001     |     |

## Why

Conversations, messages, products and leads must survive restarts and be queryable per client.

## Scope

Drizzle schema and migrations for Postgres. Every table has `client_id`.

| Table           | Purpose                                                                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| `contacts`      | One row per customer phone number per client; language, name if given, consent flags                      |
| `conversations` | Thread per contact; `status` (`bot`, `human`, `closed`), last activity                                    |
| `messages`      | Inbound and outbound messages, channel message id (unique, for dedupe), raw payload, type                 |
| `agent_runs`    | One row per agent turn: model, tokens in/out, cost estimate, tool calls, latency, errors                  |
| `products`      | Synced catalogue: variant id, SKU, title, type, vendor, price, available, tags, URL, image, search vector |
| `leads`         | Captured leads: type, fields (JSON), branch, status                                                       |
| `outbox`        | Emails and notifications produced (used by the mock mailer and the back-office panel)                     |

- `pnpm db:migrate` and `pnpm db:seed` (seeds a demo conversation).

## Acceptance criteria

- [ ] Migrations run cleanly on an empty local Postgres and on Supabase.
- [ ] Inserting a message with a duplicate channel message id is rejected.
- [ ] Product search vector is generated by the database (Portuguese and simple config).

## Out of scope

Vector embeddings (later, only if full-text search is not good enough).
